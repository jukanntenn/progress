# PRFC: A cordis-style kernel: everything in progress becomes a composable plugin

Status: proposed

English | [中文](2026-08-31-cordis-kernel-plugin-architecture.zh.md)

## Problem

progress has a privileged core, and it is growing. `cli/core.py` orchestrates the whole run — producers, reports pipeline, notification authoring, queue, dispatcher — in one function, so cross-cutting policy (dedupe, quiet hours, content budgets, secret scrubbing beyond `scrub.py`) has no insertion point except inside pipeline code. The CLI and the API each own a hand-written lifespan that repeats the same ordering knowledge (DB before config merge, observability before the `aiohttp` session, drain on exit); two copies of an invariant is one copy waiting to diverge. Scheduling lives outside the process entirely — supercronic re-runs `progress run` in the container — so bare-metal and Windows deployments have no scheduling at all, and no integration can declare its own cadence (feed polling faster than repo sync is impossible to express). Config changes written by the API's `set_config` do not reach any running capability until the next process starts.

The integrations tree is already most of a plugin architecture — `@register` plus entry_points, a five-hook protocol, self-contained packages with their own migrations, templates, and prompts — but the registry is a process-global singleton: one instance per integration, no dependency semantics, no runtime mount/unmount, and no way to run the same integration twice under different configs. Third parties can add "an integration" and nothing else: not a notification channel, not a telemetry backend, not a scheduler, not a patch to a built-in plugin's config.

The reference adaptation, deepseek-harness, demonstrates the missing mechanism at scale: cordis is a small kernel where a plugin is `apply(ctx, config)` plus three declarations (`inject`, `provide`, `Config`), boot order is expressed as service dependencies rather than sequencing code, every registration is a reversible effect disposed in reverse order, events are the only lateral extension point with five dispatch modes as public contract, and the entire application is a composition tree described as data (rows patched by id, layered) — `dsh web` versus `--profile sdk` differ only in which bundle layers stack, with no special-case code.

## Proposal

Introduce `progress.kernel`, a Python port of cordis semantics — not of its TypeScript machinery. A `Context` is a service registry resolved through `__getattr__` (underscore and protocol names raise `AttributeError` immediately so `copy`/`pickle`/`hasattr` probing never triggers resolution; `ServiceNotFound` subclasses `AttributeError` so the attribute worldview and the domain worldview agree). Typed access is `ctx.get(Type)` as the primary form — the type is exact with no stub — with an optionally generated `.pyi` stub as a drift-gated artifact for `ctx.db` sugar, the same generation-plus-gate pattern the OpenAPI chain already uses. A plugin is a function or class with `inject` (required services), optional `provide`, and `Config` as a pydantic model; a `Fiber` owns its lifecycle (`PENDING → LOADING → ACTIVE → UNLOADING/DISPOSED/FAILED`), stays pending until every injected service resolves, and reloads when a dependency's implementation changes (the epoch mechanism). Every registration inside `apply` is an effect with a reverse-order async disposer — the standing teardown idiom becomes structural, not disciplinary. Events declare their dispatch mode (`emit`, `parallel`, `serial`, `bail`, `waterfall`) in an `EventSpec` registry; the mode is public contract, checked at dispatch. `isolate` ships as a kernel primitive (scope-label chains over the service map, joining scopes by shared label) even though no profile uses it in phase one — it is the same layer as `provide`/`get`, cheap to carry, and the natural extension point for multi-instance deployments (mirrors, multiple Miniflux sources). `intercept` config merging ships with it.

Capabilities become services with a Definition (abstract `Service` declaring the ctx key), Providers (swappable implementations), and Consumers — the seam discipline from the reference:

| ctx key | Definition | Built-in providers |
| --- | --- | --- |
| `ctx.config` | layered config + `subscribe(ns)` | `config-db` (existing DB config table + seed merge) |
| `ctx.db` | connection lifecycle + migrations | `db-tortoise` (aiosqlite) |
| `ctx.http` | shared aiohttp session | `http-shared` (injects telemetry — the ordering invariant, declared) |
| `ctx.telemetry` | sink seam: `emit/flush/shutdown` + redaction waterfall | `telemetry-otel`, `telemetry-bugsink`, `telemetry-logfile` |
| `ctx.scheduler` | `every(cron, fn) -> Disposable` | `scheduler-asyncio` (in-process), `scheduler-supercronic` (container) |
| `ctx.webServer` | `register_router(r) -> Disposable` | `webserver-fastapi` (existing `api/` shell) |
| `ctx.ai` | analysis calls + global concurrency semaphore | `ai-pydantic`, `ai-replay` (tests) |
| `ctx.integrations` | instance registry | — |
| `ctx.notifications` | channel registry + dispatch | hub + one plugin per channel |
| `ctx.i18n`, `ctx.rss`, `ctx.markdown`, `ctx.gitHub`, `ctx.gitLocal` | utility services | existing modules moved |

Composition becomes data. Rows (`id`/`name`/`config`/`inject`/`disabled`) live in patch layers: a `base` profile of shared rows, with `run`, `serve`, and `all-in-one` stacking on top — the reference's bundle semantics. Patches target rows by `id` and replace whole configs; `!!py` expressions are evaluated only after the row's injections activate, so `disabled: !!py not ctx.config.value.analysis.enabled` prunes AI rows on deployments without keys — graceful degradation as declaration. `config.toml` remains the only user-facing configuration; it is translated into the user patch layer at boot, so nobody faces two config systems. `progress --dump-config` and `progress inspect` print the effective tree, fiber states, and precise missing-service names, failing loud on rows that never activated — the reference's boot diagnostics, ported.

The `core.run` pipeline becomes a thin runner plugin plus an event catalog: `run/started` (emit), `integration/pre-run` (waterfall — policy may reject), per-integration sync/run, `integration/post-run` (parallel), `report/assemble` (waterfall — AI title/summary, budgets, i18n attach here), `report/generated` (emit — persistence, MarkPost, RSS listen), `notification/build` (serial — each integration remains the sole author of its notifications, as a contract preserved by event semantics rather than a hook), `notification/dispatch` (parallel), `run/completed` (emit).

Hot update ships with layered, explicit commitments. L0: config changes drive `fiber.update()` — the `internal/update` waterfall, in-place restart — so `set_config` takes effect in a running serve. L1: compose changes are a transactional diff (create all, then remove stale, roll back on any failure) over watched composition files; mounting or unmounting an already-installed plugin never needs a restart, and dependency-driven fibers make both sides correct automatically. L2: module-level swap is restricted to plugin packages via fresh-import generation (a new module name per generation; `importlib.reload` is banned — new class objects break `isinstance` and strand module singletons); framework-surface changes fall back to process restart. L3: installing new plugins is an out-of-process command (`progress plugin add` via `uv` into the state home, appended to `sys.path` tail so plugins resolve the host kernel — the reference's shared-cordis guarantee), after which activation is just L1. `serve` and `all-in-one` run live; `run` is one-shot and composes at startup only.

Migration lands in four phases, each behavior-equivalent before the next: (1) kernel plus the unification of the two lifespans — CLI and API boot the same composed tree, the first acceptance scenario and the lowest-risk one; (2) the pipeline becomes events, with `@register` kept as a compatibility shim translating to plugin rows so third-party entry_points load unchanged; (3) seams for notifications, telemetry, AI, and scheduler; (4) composition files, in-process scheduling, and inspect/dump. Deliberately not ported, with revisit triggers recorded here: the browser-side cordis tree and `dsh.client` combo bundles (progress is a single-product SPA with no third-party UI ecosystem; the schema-driven settings pages and the OpenAPI→`schema.ts` contract chain already cover the need — settings-as-data is the only piece taken); the typert remote layer (progress's API surface is static and product-owned, which is exactly FastAPI+OpenAPI's best case); and framework module HMR (the L2 restriction above).

## Alternatives considered

**Adopt an existing Python plugin mechanism — pluggy, entry_points alone, or a DI container such as dependency-injector.** They lost: pluggy is a hook collector with no service registry, no lifecycle, and no reversible effects; entry_points (already in use) solve discovery and nothing else; DI containers wire singletons at startup but have no notion of a fiber that waits for dependencies, reloads when they change, or unwinds its registrations. None of them yield composition-as-data or dispatch-mode contracts, which is where the value is.

**Port cordis wholesale, including the Proxy-based interception and TypeScript declaration merging.** It lost: declaration merging has no Python equivalent, so the compile-time experience cannot come along regardless; the runtime semantics port cleanly onto `__getattr__`, pydantic, and asyncio (async disposers are more natural in Python than in JS), so the machinery buys nothing here. The type experience is rebuilt natively — `ctx.get(Type)` exact typing plus generated stubs under the existing drift-gate pattern.

**Descriptors (with a metaclass installing service slots) instead of `__getattr__` resolution.** It lost: the service namespace is an open runtime registry, while descriptors are static class-body declarations — every new service would mutate the `Context` class at import time (import-order coupling, the global-state smell the kernel exists to remove), and type checkers do not execute runtime setattr, so the promised typing benefit still requires static generation. Third-party services would remain second-class citizens forever.

**Stay incremental: slim `core.run`, factor the lifespans into one shared function, keep the architecture.** It lost: it treats symptoms — the shared lifespan function still encodes ordering by hand, scheduling stays outside the process, config stays cold, the integration registry stays a singleton that cannot run two instances, and third parties still get one extension point. The cost is comparable to phase 1+2 while capping the ceiling at "tidier monolith".

**Port the browser plugin tree (`dsh.client` combo bundles, SSE HMR, slots) and the typert RPC layer now.** They lost for now, not forever: both exist to let third parties ship UI and typed RPC into a running host without rebuilding its frontend — a distribution-ecosystem problem progress does not have. The revisit triggers: a third-party integration needs custom report components (start with a server-side widget descriptor, which is data), or an external agent must drive progress programmatically (that is an sdk-style profile plugin, not typert).

## Acceptance criteria

Kernel unit tests pass over: effect reverse-order disposal with per-disposer exception isolation; pending→activation ordering; provider-reload cascading to dependents; waterfall veto and serial short-circuit; isolate shadowing and scope joining; `update()` hot reload; expression evaluation deferred until injections resolve. The CLI `run` and API `serve` commands boot one composed tree and `cli/lifespan.py` plus the API lifespan are deleted. A `set_config` write observably reaches a running serve without restart (channel or language change takes effect live). A cron row executes in-process under `scheduler-asyncio`, and a container deployment no longer requires supercronic for scheduled runs. `progress --dump-config` and `progress inspect` print the effective tree with fiber states, and a row that fails to activate reports the exact missing service names and fails loud. Compose updates are transactional: a row whose activation fails rolls back its siblings (tested). The existing test suite (`uv run pytest`) stays green through every phase, and a third-party integration discovered via entry_points loads unchanged behind the `@register` shim.

## Risks

The kernel is self-maintained infrastructure — the largest single cost of this proposal, roughly 500–800 lines plus an equivalent weight of tests; it is mitigated by porting semantics only (the reference implementation is the oracle for every mechanism) and by the four-phase plan letting the effort stop at any phase with value banked. Debugging stacks get deeper; the mitigation is that inspect/dump and fail-loud activation diagnostics ship in the same phase as the kernel, not later — a kernel without them would be a regression in operability. Two configuration surfaces could confuse users; `config.toml` stays the sole user interface and patch layers remain deployment artifacts, enforced by documentation rather than discipline. The fiber state machine's async reentrancy (disposal ordering, epoch races) is genuinely subtle; the mitigation is porting the reference's epoch/inertia design decisions instead of inventing them, with stress tests around reload-during-unload. Hot-update has Python-specific footguns — module-level state outside effects, C extensions that never unload, zombie generations; the mitigations are the effect-only registration contract, inspect auditing for violations, and L2 remaining a restricted, restart-fallback capability rather than a promise. Finally, team unfamiliarity with the style is real; every phase lands behavior-equivalent first, so a revert is always a bounded, local decision.
