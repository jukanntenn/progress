# PRFC: A cordis-style kernel: everything in progress becomes a composable plugin

Status: implemented

English | [中文](2026-08-31-cordis-kernel-plugin-architecture.zh.md)

## Problem

progress has a privileged core, and it is growing. `cli/core.py` orchestrates the whole run — producers, reports pipeline, notification authoring, queue, dispatcher — in one function, so cross-cutting policy (dedupe, quiet hours, content budgets, secret scrubbing beyond `scrub.py`) has no insertion point except inside pipeline code. The CLI and the API each own a hand-written lifespan, and the four `progress users` subcommands hand-roll a fourth micro-variant each (bare `init_db`/`close_db` pairs, no migration, no merge), repeating the same ordering knowledge (DB before config merge, observability before the `aiohttp` session, drain on exit); multiple copies of an invariant are copies waiting to diverge. Scheduling lives outside the process entirely — supercronic re-runs `progress run` in the container — so bare-metal and Windows deployments have no scheduling at all, and no integration can declare its own cadence (feed polling faster than repo sync is impossible to express). Config changes written by the API's `set_config` do not reach any running capability until the next process starts.

The integrations tree is already most of a plugin architecture — `@register` plus entry_points, a five-hook protocol, self-contained packages with their own migrations, templates, and prompts — but the registry is a process-global singleton: one instance per integration, no dependency semantics, no runtime mount/unmount, and no way to run the same integration twice under different configs. Third parties can add "an integration" and nothing else: not a notification channel, not a telemetry backend, not a scheduler, not a patch to a built-in plugin's config.

The reference adaptation, deepseek-harness, demonstrates the missing mechanism at scale: cordis is a small kernel where a plugin is `apply(ctx, config)` plus three declarations (`inject`, `provide`, `Config`), boot order is expressed as service dependencies rather than sequencing code, every registration is a reversible effect disposed in reverse order, events are the only lateral extension point with five dispatch modes as public contract, and the entire application is a composition tree described as data (rows patched by id, layered) — `dsh web` versus `--profile sdk` differ only in which bundle layers stack, with no special-case code.

## Decision

Introduce `progress.kernel`, a Python port of cordis semantics — not of its TypeScript machinery. A `Context` is a service registry resolved through `__getattr__` (underscore and protocol names raise `AttributeError` immediately so `copy`/`pickle`/`hasattr` probing never triggers resolution; `ServiceNotFound` subclasses `AttributeError` so the attribute worldview and the domain worldview agree). Typed access is `ctx.get(Type)` as the primary form — the type is exact with no stub. The optionally generated `.pyi` stub for the `ctx.db` sugar was evaluated during implementation and dropped: a module-level stub replaces the implementation's own class symbol for every importer, conflicting with the kernel's internal typing; `ctx.get(Definition)` already carries exact types (it was always the primary form). A plugin is a function or class with `inject` (required services), optional `provide`, and `Config` as a pydantic model; a `Fiber` owns its lifecycle (`PENDING → LOADING → ACTIVE → UNLOADING/DISPOSED/FAILED`), stays pending until every injected service resolves, and reloads when a dependency's implementation changes (the epoch mechanism). Every registration inside `apply` is an effect with a reverse-order async disposer — the standing teardown idiom becomes structural, not disciplinary. Events declare their dispatch mode (`emit`, `parallel`, `serial`, `bail`, `waterfall`) in an `EventSpec` registry; the mode is public contract, checked at dispatch. `ServiceNotFound(AttributeError)` and the runtime `EventSpec` registry are Python-side designs rather than ports — cordis has neither an exception class nor a runtime event registry (it relies on TS declaration merging and compile-time checks); the registry moves the mode-as-contract guarantee the reference enforces via a catalog gate into the kernel itself. bail and serial collapse semantically in an all-async runtime (in-order, short-circuit on first truthy); the five names stay as public contract, bail implemented as serial's veto alias. `isolate` ships as a kernel primitive (scope-label chains over the service map, joining scopes by shared label) even though no profile uses it in phase one — it is the same layer as `provide`/`get`, cheap to carry, and the natural extension point for multi-instance deployments (mirrors, multiple Miniflux sources). `intercept` config merging ships with it.

Capabilities become services with a Definition (abstract `Service` declaring the ctx key), Providers (swappable implementations), and Consumers — the seam discipline from the reference:

| ctx key | Definition | Built-in providers |
| --- | --- | --- |
| `ctx.config` | layered config + `subscribe(ns)` | `config-db` (existing DB config table + seed merge) |
| `ctx.db` | connection lifecycle + migrations | `db-tortoise` (aiosqlite) |
| `ctx.http` | shared aiohttp session | `http-shared` (injects telemetry — the ordering invariant, declared) |
| `ctx.telemetry` | sink seam: `emit/flush/shutdown` + redaction waterfall | `telemetry-otel`, `telemetry-bugsink`, `telemetry-logfile` |
| `ctx.scheduler` | `every(cron, fn) -> Disposable` | `scheduler-asyncio` (in-process; croniter, per-entry mutual exclusion with skip, no catch-up) |
| `ctx.webServer` | `register_router(r) -> Disposable` | `webserver-fastapi` (existing `api/` shell) |
| `ctx.ai` | analysis calls + global concurrency semaphore | `ai-pydantic`, `ai-replay` (tests) |
| `ctx.integrations` | instance registry | — |
| `ctx.notifications` | channel registry + dispatch | hub + one plugin per channel |
| `ctx.i18n`, `ctx.rss`, `ctx.markdown`, `ctx.gitHub`, `ctx.gitLocal` | utility services | existing modules moved |

Composition becomes data. Rows (`id`/`name`/`config`/`inject`/`disabled`) live in patch layers: a shipped `base` profile with `run`, `serve`, and `all-in-one` stacking on top, then the state-home user patch, plugin rows, and a `--patch` debug overlay — the reference's bundle semantics. Composition artifacts are TOML, not the reference's YAML (tomlkit is already a dependency, round-trips with comments, and operators face a single syntax); deferred expressions ride an inline-table convention (`disabled = { _py = "not ctx.config.analysis.enabled" }`) — a deliberate deviation whose evaluation semantics match the reference clause for clause: evaluated only after the row's injections activate, `disabled` re-evaluated at every mount decision, dumped unevaluated; the evaluator is a restricted eval (empty builtins plus a whitelist), failing loud with the row id. Rows carry structure only: existence/disabled/inject/cadence belong to rows, while all business config — built-in and third-party — flows through DB config-table namespaces (`subscribe(ns)` on `ctx.config`), keeping the single source of truth. `config.toml` remains the only user-facing configuration; its translation into the patch layer thins to structural derivation (pruning AI rows on keyless deployments), overlapping the existing seed path, so nobody faces two config systems. `progress --dump-config` and `progress inspect` print the effective tree, fiber states, and precise missing-service names, failing loud on rows that never activated — the reference's boot diagnostics, ported.

The `core.run` pipeline becomes a thin runner plugin plus an event catalog: `run/started` (emit), `integration/pre-run` (waterfall — policy may reject), per-integration sync/run, `integration/post-run` (parallel), `report/assemble` (waterfall — AI title/summary, budgets, i18n attach here), `report/generated` (emit — persistence, MarkPost, RSS listen), `notification/build` (serial — each integration remains the sole author of its notifications, as a contract preserved by event semantics rather than a hook), `notification/dispatch` (parallel), `run/completed` (emit). The firing granularity is streaming: the three event families fire per subject as it completes, equivalent to the current T9 streaming semantics (an integration that finishes early reports and dispatches early); barrier-style consumption (digest) is implemented as an accumulating policy listener — the reverse is impossible, which is the decisive argument for streaming. `notification/build`'s payload carries an accumulator filled by the target integration, preserving the sole-author contract; serial means in-order within a dispatch with short-circuit on first truthy, and concurrent dispatches do not mutually exclude (equivalent to today; documented in the catalog, no false global-ordering promise). The runner plugin carries the pipeline as a background task: apply registers and returns, the fiber goes ACTIVE, and the task is cancelled via its effect.

Hot update ships with layered, explicit commitments. L0: `set_config(ns)` notifies through the config service, re-evaluating the deferred expressions of affected rows; changed rows run `fiber.update()` — the `internal/update` waterfall, in-place restart — cascading to their dependents via epoch: a row-precise reload rather than a tree rebuild (heavy services that inject no volatile sections stay untouched), so channel or language changes take effect live in a running serve. L1: compose changes are a transactional diff (create all, then remove stale, roll back on any failure) triggered by explicit signals — SIGHUP, an extended `POST /config/reload`, and `progress plugin` commands auto-triggering; no background file watching (container signals are native and inotify under bind mounts is unreliable — a deviation from the reference). Mounting or unmounting an already-installed plugin never needs a restart, and dependency-driven fibers make both sides correct automatically. L2: module-level swap is restricted to plugin packages via fresh-import generation (a new module name per generation; `importlib.reload` is banned — new class objects break `isinstance` and strand module singletons), shipped disabled by default behind `--dev-plugin-watch` — matching the reference's own practice, whose base bundle disables its hmr row; framework-surface changes fall back to process restart. L3: installing new plugins is an out-of-process command (`progress plugin add` via `uv --target state_home/plugins --no-deps`, appended to the `sys.path` tail so plugins resolve the host kernel — plugins must not declare progress as a dependency; progress not being on PyPI is the shared-cordis guarantee), after which activation is just L1. `serve` and `all-in-one` run live; `run` is one-shot and composes at startup only.

Migration lands in four phases, each behavior-equivalent before the next, with zero DB schema changes across the whole plan (the config table is KV JSON; reverting any phase is a PR revert with no data entanglement): (1) the kernel plus lifespan unification — a `runtime/` package holds nine service entries (db/config/three telemetry backends/auth/i18n/git-proxy/http), `compose_base()` becomes the single ordering authority, CLI and API boot the same composed tree, and the four hand-rolled `users` bootstraps fold in; `http` injects `telemetryOtel` to name the OTel-instrumentor arming order (the one dependency seam-ization cannot derive from inject alone); (2) the pipeline becomes events, with `@register` kept as a compatibility shim translating to plugin rows while integration config stays instance-loaded from DB sections, third-party entry_points unchanged, and the legacy aggregation path (`run_notifications` et al) deleted along with its rewritten tests; (3) seams for notifications, telemetry, AI, and scheduler — telemetry is a hub with multiple backends, the redaction waterfall keeps `scrub.py` as the innermost default and leaves the `metrics.py` function surface untouched; auth sinks into the base tree (a beyond-equivalence fix: cron-only deployments bootstrap on first run, idempotent); the scheduler lands as the croniter-backed service; (4) composition files, in-process scheduling (the `scheduled-run` consumer plus the `schedule.cron` config section plus supercronic retirement — the `scheduler-supercronic` provider is removed from the service table accordingly: acceptance already frees containers from supercronic, and once scheduling runs in process nothing needs the app to generate crontabs in reverse), inspect/dump, and L2/L3 (L2 ships as the generation-import primitive plus a stdlib polling watcher — no fs-event dependency — scoped to third-party plugin packages). AI keeps its call sites untouched: the module-level `run_extraction` routes through the active `ctx.ai` handle (the same funnel pattern as telemetry), so existing per-module test patches keep working; `Components.ai` still ships, populated by the shim. The serve tree mounts integrations + runner + the scheduled-run row itself, making serve the all-in-one capable profile (``run`` stays the one-shot subset). Folding `users` in makes `migrate_config_data` run there too — a safe superset recorded as a deliberate deviation. Deliberately not ported, with revisit triggers recorded here: the browser-side cordis tree and `dsh.client` combo bundles (progress is a single-product SPA with no third-party UI ecosystem; the schema-driven settings pages and the OpenAPI→`schema.ts` contract chain already cover the need — settings-as-data is the only piece taken); the typert remote layer (progress's API surface is static and product-owned, which is exactly FastAPI+OpenAPI's best case); and framework module HMR (the L2 restriction above).

## Alternatives considered

**Adopt an existing Python plugin mechanism — pluggy, entry_points alone, or a DI container such as dependency-injector.** They lost: pluggy is a hook collector with no service registry, no lifecycle, and no reversible effects; entry_points (already in use) solve discovery and nothing else; DI containers wire singletons at startup but have no notion of a fiber that waits for dependencies, reloads when they change, or unwinds its registrations. None of them yield composition-as-data or dispatch-mode contracts, which is where the value is.

**Port cordis wholesale, including the Proxy-based interception and TypeScript declaration merging.** It lost: declaration merging has no Python equivalent, so the compile-time experience cannot come along regardless; the runtime semantics port cleanly onto `__getattr__`, pydantic, and asyncio (async disposers are more natural in Python than in JS), so the machinery buys nothing here. The type experience is rebuilt natively — `ctx.get(Type)` exact typing plus generated stubs under the existing drift-gate pattern.

**Descriptors (with a metaclass installing service slots) instead of `__getattr__` resolution.** It lost: the service namespace is an open runtime registry, while descriptors are static class-body declarations — every new service would mutate the `Context` class at import time (import-order coupling, the global-state smell the kernel exists to remove), and type checkers do not execute runtime setattr, so the promised typing benefit still requires static generation. Third-party services would remain second-class citizens forever.

**Stay incremental: slim `core.run`, factor the lifespans into one shared function, keep the architecture.** It lost: it treats symptoms — the shared lifespan function still encodes ordering by hand, scheduling stays outside the process, config stays cold, the integration registry stays a singleton that cannot run two instances, and third parties still get one extension point. The cost is comparable to phase 1+2 while capping the ceiling at "tidier monolith".

**Port the browser plugin tree (`dsh.client` combo bundles, SSE HMR, slots) and the typert RPC layer now.** They lost for now, not forever: both exist to let third parties ship UI and typed RPC into a running host without rebuilding its frontend — a distribution-ecosystem problem progress does not have. The revisit triggers: a third-party integration needs custom report components (start with a server-side widget descriptor, which is data), or an external agent must drive progress programmatically (that is an sdk-style profile plugin, not typert).

## Consequences

Verified by the test suite:

Kernel unit tests pass over: effect reverse-order disposal with per-disposer exception isolation; pending→activation ordering; provider-reload cascading to dependents; waterfall veto and serial short-circuit; isolate shadowing and scope joining; `update()` hot reload; expression evaluation deferred until injections resolve. The CLI `run` and API `serve` commands boot one composed tree, `cli/lifespan.py` and the API lifespan's ordering knowledge are deleted (the ASGI hook itself remains as a roughly five-line boot shim), and `progress users`' hand-written bootstrap folds into the same tree. A `set_config` write observably reaches a running serve without restart (channel or language change takes effect live). A cron row executes in-process under `scheduler-asyncio`, and a container deployment no longer requires supercronic for scheduled runs. `progress --dump-config` and `progress inspect` print the effective tree with fiber states, and a row that fails to activate reports the exact missing service names and fails loud. Compose updates are transactional: a row whose activation fails rolls back its siblings (tested). The existing test suite (`uv run pytest`) stays green through every phase, and a third-party integration discovered via entry_points loads unchanged behind the `@register` shim.

Residual risks and their mitigations:

The kernel is self-maintained infrastructure — the largest single cost of this proposal, roughly 1200–1600 lines plus an equivalent weight of tests (a field survey of the cordis core measures 2409 lines of TS; the original 500–800 estimate was optimistic — fiber's epoch/effect/inertia machinery has no Proxy plumbing to shed and is exactly what is being bought), with the composition loader adding roughly 800–1200 more in phase four; it is mitigated by porting semantics only (the reference implementation is the oracle for every mechanism), by shipping boot diagnostics in the same phase as the kernel, and by the four-phase plan letting the effort stop at any phase with value banked (zero DB schema changes keep every revert a data-free PR revert). Debugging stacks get deeper; the mitigation is that inspect/dump and fail-loud activation diagnostics ship in the same phase as the kernel, not later — a kernel without them would be a regression in operability. Two configuration surfaces could confuse users; `config.toml` stays the sole user interface and patch layers remain deployment artifacts, enforced by documentation rather than discipline. The fiber state machine's async reentrancy (disposal ordering, epoch races) is genuinely subtle; the mitigation is porting the reference's epoch/inertia design decisions instead of inventing them, with stress tests around reload-during-unload. serial and bail have zero production call sites in the reference (surveyed); `notification/build` is serial's first production use — its semantics pinned by the catalog documentation and covered by tests. Hot-update has Python-specific footguns — module-level state outside effects, C extensions that never unload, zombie generations; the mitigations are the effect-only registration contract, inspect auditing for violations, and L2 remaining a restricted, restart-fallback capability rather than a promise. Finally, team unfamiliarity with the style is real; every phase lands behavior-equivalent first, so a revert is always a bounded, local decision.
